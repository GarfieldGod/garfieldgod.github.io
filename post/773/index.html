1. Chunk地图分块核心概念

  1. 不要在编辑器场景直接摆放上万Chunk实例，运行会一次性全部实例化，帧率暴跌。
  2. 编辑器存放的是配置数据/预制资源，运行时根据玩家位置动态实例化。
  3. 编辑态可以完整编辑地图，运行态只加载视距范围内Chunk；远处卸载。
  4. 远景处理：不加载完整实例，使用简化模型/LOD/烘焙远景。
  5. Chunk不要直接用世界坐标字符串作为资源地址；建议使用结构体ChunkKey(depth,lx,ly)标识。
  6. 流式加载本质：数据常驻内存，GameObject按需实例化销毁。

误区：不是所有Chunk都是相同预制；真实开放世界每个Chunk资源内容不一样，对象池对不同内容Chunk收益很低；对象池适合重复物体（树木石头）。

2. 四叉树 Quadtree

  1. 2D平面空间划分，每个节点分裂4个子节点；达到最大深度得到叶子Chunk。
  2. 根节点代表整个大世界Bounds；只有叶子节点对应实际Chunk数据。
  3. 深度depth=N，叶子总数 = $4^{depth}$；depth=6 → 4096个叶子块。
  4. 不要用连续整数ID作为资源寻址；使用三元标识：depth, localX, localY。
  5. 结构体ChunkKey作为唯一主键，用来做字典key。
  6. 根节点depth=0；不断Subdivide分裂，到达maxDepth停止分裂生成ChunkData。

四叉树节点结构

  • Bounds：该节点世界包围盒
  • Depth：树深度
  • children：4个子节点数组；叶子节点children=null
  • associatedChunk：叶子节点绑定ChunkData

3. Bounds Unity结构体

  1. Bounds = center中心点 + extents半长宽；代表轴对齐包围盒AABB。
  2. 用途：判断玩家是否在区块范围内，碰撞检测，四叉树空间判断。
  3. Bounds.Intersects(other) 判断两个包围盒相交。
  4. Bounds.Contains(point) 判断点是否在包围盒内部。

注意：Bounds是结构体值类型，赋值拷贝。

4. Addressables资源加载原理

var handle = Addressables.LoadAssetAsync<GameObject>(addr);
await handle.Task;
GameObject prefabTemplate = handle.Result;
GameObject instance = Instantiate(prefabTemplate);
  1. LoadAssetAsync：把预制模板资源加载进内存，不会生成场景GameObject实例。
  2. Instantiate：复制模板，生成场景实例对象。
  3. Release(handle)：释放模板资源；不会销毁已经Instantiate出来的实例。
  4. 实例和模板是两份独立对象；实例不持有模板资源句柄。
  5. 不建议加载完成立刻Release模板；频繁加载释放会有性能开销。
  6. Addressables适合大项目动态资源；小项目可以直接使用预制引用。

误区：Release之后已经实例化出来的GameObject不会消失；模板卸载只是释放内存中的源预制。

5. 对象池 ObjectPool

作用

复用GameObject，减少频繁Instantiate/Destroy开销；适合大量重复物体（树、道具）。

核心概念

  1. 初始化预先创建N个对象，SetActive(false)存入Queue队列。
  2. 获取：Dequeue取出，SetActive(true)，设置位置旋转。
  3. 归还：不用的物体SetActive(false)重新入队列。
  4. 动态扩容：池子为空时Instantiate新对象。
  5. 最大池上限maxPoolSize：超过上限归还时直接Destroy，防止内存无限膨胀。

缺陷

  1. 如果物体全部不一样（每个Chunk模型纹理不同）对象池收益很小。
  2. 区域切换后，池子残留大量不用对象，占用内存；需要支持缩容策略。
  3. 对象池本身非线程安全；多线程访问需要lock。

注意：对象池存的是GameObject实例，不是Prefab模板资源。

6. 异步限流调度器 AsyncLimiter

目标：控制最大并发加载数量 + 任务优先级；防止同时启动大量Addressables加载任务卡死。

组成部分

  1. _maxConcurrent：最大同时运行任务数量。
  2. _runningCount：当前正在运行任务计数。
  3. 优先队列：PriorityQueue<Func<Task>,AsyncPriority>。
  4. 枚举优先级：High=0，Normal=1，Low=2；最小堆，数值越小优先级越高。

关键设计：Func<Task>作为入参

  1. Func<Task>：保存一个尚未执行的异步函数（菜谱）。
  2. .Invoke() 才真正启动任务。
  3. ❌不能传入Task；传入Task方法调用瞬间任务就已经开始执行，限流优先级全部失效。

调度流程

  1. Enqueue：把Func<Task>放入优先队列；触发_ = RunScheduler()。
  2. RunScheduler加锁判断：如果并发未满并且队列有任务，取出Func，runningCount++。
  3. 执行await func.Invoke()执行业务加载。
  4. finally：runningCount--，再次调用_ = RunScheduler()消费下一条任务。
  5. 废弃任务处理：不支持队列内删除；任务取出执行时内部判断标记，不需要直接return跳过。

重要代码规范

  1. 禁止async void业务调度函数。
  2. 使用async Task，调用处显式_ = RunScheduler()丢弃Task，消除编译器CS4014警告。
  3. 调度器外层增加try‑catch兜底，捕获调度器自身异常。

7. Task / async / await / async‑void / Func<Task>

  1. Task：代表异步操作的状态容器；Task无返回；Task<T>带返回值。Task对象不等于正在运行，只是记录状态。
  2. await：等待Task完成；释放当前线程，不阻塞主线程。
  3. async void：业务代码严禁使用；没有Task对象；异常直接全局抛出造成Unity崩溃；仅适用于UI事件回调。
  4. async Task：返回Task对象；异常封装在Task内部，不会直接崩溃。
  5. _ = MethodAsync()：丢弃运算符Discard；显式告诉编译器故意不等待Task，消除CS4014警告；Task对象仍然存在内存。
  6. Func<Task>委托：保存异步函数，实现延迟执行；调度器控制何时启动任务。

注意：_=丢弃不等于async‑void；两者本质不同。丢弃Task后，如果不await，内部异常会静默隐藏，需要内部try‑catch。

8. 多线程基础 lock、线程安全、死锁

lock(object _lock)互斥锁

private readonly object _lock = new object();
lock(_lock)
{
    //临界区：同一时刻只允许一个线程执行
}
  1. 保护共享资源：集合、计数器；防止多线程读写冲突。
  2. lock块内只做简单读写，严禁写await，会造成锁不释放，死锁。
  3. lock离开大括号自动释放；异常也会释放锁。

线程安全

定义：多线程同时访问对象，不会崩溃、数据错乱。

  1. .NET普通集合List/Dictionary/手写PriorityQueue 非线程安全。
  2. Concurrent开头集合（ConcurrentQueue）内部自带锁，线程安全。
  3. 规则：只要有线程写数据，读和写全部需要同步保护；只读无写不需要锁。
  4. 即使读取Count属性，有并发写的时候也需要lock，防止读到脏中间状态。

死锁 Deadlock

四个条件同时发生产生死锁：互斥、持有并等待、不可抢占、循环等待。 典型场景：线程1持有锁A等待锁B；线程2持有锁B等待锁A，互相永久等待。

避免策略：

  1. 尽量避免嵌套lock。
  2. 如果多锁，所有线程获取锁顺序保持统一。
  3. lock块短小，不要放等待、外部业务调用。

内存可见性

普通int读写原子，但多CPU缓存可能读到旧值；lock会插入内存屏障读取最新值。

9.手写最小堆 PriorityQueue原理

底层List实现最小堆；父节点小于等于两个子节点；左右子节点之间没有大小约束。

下标关系：

  • 父索引：(idx‑1)/2
  • 左孩子：idx*2+1
  • 右孩子：idx*2+2

HeapifyUp 上浮（入队Enqueue）

  1. 将新元素追加到数组末尾。
  2. 和自己父节点比较；如果比父小，交换；更新idx为父索引。
  3. 重复直到不小于父节点，或者到达堆顶。

上浮只和父比较，完全不看兄弟节点。

HeapifyDown下沉（出队Dequeue）

  1. 取出堆顶元素；数组最后一个元素移动到堆顶位置。
  2. 当前节点同时对比左孩子、右孩子；三者选出最小值下标smallest。
  3. 如果smallest不是自己，交换；idx = smallest继续向下循环。
  4. 直到当前节点最小或者到达叶子节点。

下沉会同时看左右两个子节点。

重要约束

  1. HeapifyUp / HeapifyDown只做局部修复；不会全局扫描修复堆。
  2. 禁止外部直接修改底层List；外力修改会破坏堆结构，队列没有自动纠错能力。
  3. 最小堆：数值越小优先级越高；业务尽量对齐语义，避免业务层传负数。

工程妥协：堆无法删除中间元素；作废任务只能弹出后过滤。

10. 流式系统 DynamicWorldStreamer 工程实践要点

10.1 快照（Snapshot）设计

  1. **不要直接读取实时viewer.position / viewer.forward**做一轮流式计算。
  2. 使用快照变量_lastViewerPos、_lastViewerForward保存触发Streaming那一刻的位置和朝向。
  3. 一轮完整Streaming流程（四叉树查询、距离判断、卸载判断、优先级计算）全部复用同一套快照。
  4. 风险：
    • 脚本Update执行顺序不确定，直接读Transform可能拿到错位坐标。
    • 如果后续加入await，async函数跨帧，玩家移动/转头，同批次Chunk计算基准撕裂。
    • 移动阈值判断moveDistanceToUpdate依赖上一次触发的快照位置。

10.2 成员List复用 vs 局部new List

  1. 成员字段 + Clear()复用List：只在构造时分配一次堆内存，每次Clear()清空元素，底层数组容量保留，消除每轮new带来的GC Alloc。
  2. 缺点：属于共享状态，必须靠_isUpdatingStreaming重入锁保护；如果锁失效，异步重入会把上一轮数据覆盖错乱。
  3. 局部new List：每轮独立实例，隔离安全；代价是频繁堆分配，累积GC卡顿。
  4. 最佳实践：流式查询集合提升为成员缓存，调用前.Clear()复用。

10.3 卸载分帧策略

  1. 禁止检测到需要卸载就foreach批量执行卸载；大量ReturnToPool、SetActive(false)会产生单帧CPU尖峰。
  2. 把待卸载Chunk推入Queue<ChunkData>，在Update循环限制maxUnloadPerFrame，每帧消费固定数量。
  3. ❌Queue.Contains()是O(n)遍历，Chunk数量大性能差； ✅替代方案：ChunkData增加布尔标记isQueuedForUnload，入队打标记、出队清除标记，O(1)防重复入队。
  4. 卸载队列堆积风险：玩家高速移动瞬间生成大量待卸载块，队列变长，旧Chunk会多占若干帧内存，缓慢回收。

10.4 加载优先级实现（扇形优先级）

  1. 使用Vector3.Dot(forward, dirToChunk)点积判断区块相对玩家朝向：
  • dot≈1：正前方；dot=0：侧面90°；dot≈‑1：背后。
  1. 阈值划分：High（正前方扇形）> Normal（侧面）> Low（背后）。
  2. 注意：优先级只控制加载先后顺序，不控制是否加载；是否在视距内由距离判定。
  3. 必须把优先级交给调度器优先队列；不能foreach直接全部发起加载请求，否则优先级完全失效。
  4. 同优先级下，叠加距离排序：离玩家更近的Chunk优先加载。

10.5 查询范围：AABB盒子与球形加载范围

  1. new Bounds(center,size)生成轴对齐立方体盒子；四叉树QueryVisibleChunks返回盒子相交的节点。
  2. 误区：把Bounds直接当成球形加载范围；盒子四角会查出超出球形半径的Chunk。
  3. 解决方案：拿到查询结果列表后，二次球形距离过滤，剔除超出loadingRange的区块。

10.6 集合查询性能

  1. List<T>.Contains() O(n)线性遍历；Chunk数量上涨后开销明显。
  2. 活跃Chunk建议用HashSet<ChunkData>维护，Contains变为O(1)。

10.7 async void 在流式更新中的坑

  1. async void UpdateStreaming()当前依靠_isUpdatingStreaming重入锁保证安全。
  2. 隐患：一旦函数内部加入await，函数会切到下一帧，锁会提前释放，允许第二次进入函数，造成并发重入。
  3. 建议：业务尽量避免async void；如果必须使用，不要在函数内部写await。

10.8 高速移动带来的问题（限流分帧不能保证帧率恒定）

加载限流 + 卸载分帧只能消除毁灭性单帧尖峰，不能保证无论玩家跑多快帧率完全不变。

  1. 四叉树查询、集合对比本身是主线程CPU开销；移动越快，单次需要处理Chunk越多。
  2. 加载队列堆积：虽然并发有限流，但大量任务排队，Addressables回调、实例化Awake/OnEnable带来持续CPU抖动。
  3. 卸载队列堆积：旧Chunk还没有来得及分帧回收，场景物体数量峰值升高，渲染Culling、DrawCall、物理开销上涨。
  4. 开放世界工程策略：高速移动时动态缩小加载半径，降低同时需要处理Chunk数量。

10.9 边界防抖动

  1. 卸载半径unloadingRange > 加载半径loadingRange，形成缓冲带，防止Chunk在视距边界反复加载卸载（乒乓闪烁）。

11. 工程踩坑汇总

  1. ❌不要场景里面直接放置成千上万个Chunk，运行一次性全部加载卡顿。
  2. ❌不要async void写调度业务；会异常直接崩溃。
  3. ❌不要lock块内部写await。
  4. ❌调度器入参不要直接传Task，要用Func<Task>实现延迟启动。
  5. ❌不要直接外部修改PriorityQueue底层List，堆结构损坏。
  6. ❌多线程访问非线程安全集合不加lock，出现随机崩溃脏数据。
  7. ❌不要用字符串世界坐标作为资源寻址；优先ChunkKey结构体。
  8. ✅废弃任务不在队列删除；任务取出执行的时候判断标记直接return。
  9. ✅_ = asyncTaskMethod()只是消除警告，异常依然会隐藏；函数内部必须try‑catch兜底。
  10. ✅Addressables模板资源不要频繁Load/Release；适当缓存模板句柄。
  11. ❌不要直接读取实时viewer.position/forward作为一轮流式计算的数据源，必须使用快照。
  12. ❌Queue不要频繁调用Contains，大数据量会产生大量遍历开销，改用对象布尔标记。
  13. ❌不要把AABB Bounds当作球形加载范围，盒子四角会查询多余Chunk，需要二次距离过滤。
  14. ❌不要foreach直接批量发起加载，会绕过优先队列，优先级失效。
  15. ⚠️async void即使有重入锁，函数内部不要写await，锁会提前释放引发并发。
  16. ⚠️加载限流、卸载分帧只能削除尖峰，无法完全抵消高速移动带来的平均帧率下降。
